# 가족 생활 데이터 앱 — 서비스 설계 초안

> 구현 버전과 달라진 선택, 배포·검증 범위는 [배포 안내](deployment.md)를 기준으로 확인한다. 아래는 설계 기준이며 아직 제공하지 않는 후속 기능도 포함한다.

> 2026-09-08. [아키텍처 v3](architecture-design.md)의 화면·데이터·MCP 설계다. [홈카페 요구사항](home-cafe/DESIGN.md)과 [기존 와인 스킬](wine-celler/skill.md)을 근거로 작성했다. 원본은 보존하며 아래의 변경 제안과 구분한다.

## 1. 앱의 모습

PC에서는 왼쪽 메뉴, 휴대폰에서는 하단 메뉴로 **홈 / 커피 / 와인 / 설정**을 이동한다. 공통 레이아웃에 현재 가족과 사용자를 표시한다. 서비스마다 별도 로그인이나 앱을 만들지 않는다.

| 페이지 | 핵심 내용 | 주요 행동 |
|---|---|---|
| `/` | 추천 원두, 보유 와인 병수, 최근 가족 기록 | 커피·와인 상세 이동 |
| `/coffee` | 이미지 카드/표, 브랜드·배전·내 상태·추천 필터 | 원두 등록, 평가, 세팅 확인 |
| `/coffee/beans/[id]` | 상품·1kg 가격·가족별 평가·머신 세팅 | 내 평가·세팅 저장, 상품 링크 열기 |
| `/coffee/brands` | 브랜드명·스토어 링크·설명 | 등록·수정·원두 보기 |
| `/wine` | 보유 와인, 종류·국가·빈티지 필터 | 입고, 1병 소비, 상세 보기 |
| `/wine/[id]` | 구매·소비 이력, 잔량, 가족별 시음 | 구매 추가, 소비·평가, 기록 정정 |
| `/wine/glasses` | 보유 와인잔 | 등록·수정 |
| `/settings` | 가족 구성원, 머신, 내 AI 연결·scope | 가족 허용 목록·머신 관리, 연결 폐기 |

필터·정렬은 URL에 남겨 상세 페이지에서 돌아와도 유지한다. 페이지 진입과 저장 성공 시 갱신한다. 재고는 서버 확정 값을 표시한다. 통신 오류로 저장 여부를 알 수 없으면 “결과 확인 필요”로 안내하고 같은 요청 키로 결과를 재확인한다.

웹 내장 AI 채팅 없이도 외부 AI가 MCP로 조회·등록·추천을 할 수 있다. 앱 안에서 질문하고 싶어지면 `/ask`를 추가한다. 외부 AI 연결과 웹 자체 모델 호출은 서로 다른 기능이다.

## 2. 공통 데이터 원칙

- 초기는 가족 공간 1개다. 향후 분리를 위해 도메인 데이터에 `household_id`를 둔다. 범용 다중 가족 관리 화면까지 만들지는 않는다.
- 제품·재고는 가족 공용이다. 평가·추천 여부·머신 세팅은 작성자별이며 MVP에서는 가족에게 공유한다.
- 원두와 와인을 하나의 `items` + 자유 JSON 테이블로 합치지 않는다. 도메인별 관계·검증을 유지하고 인증·페이지 틀·변경 이력을 공통화한다.
- ID는 DB 생성 UUID 등을 사용한다. 화면용 와인 번호는 별도 sequence/identity로 발급하며 최댓값 + 1 방식은 사용하지 않는다.
- 생성·수정 시각은 UTC `timestamptz`, 구매일·시음일은 `date`로 저장한다. 표시와 “오늘” 기준은 가족의 `Asia/Seoul`이다.
- 가격은 정수 또는 고정 소수 정밀도로 저장한다. 미입력은 `null`이며 0원·평점 0·비추천·재구매 안 함과 다르다.
- 수정 충돌을 감지할 주요 레코드에 `version`을 둔다. 이력이 연결된 제품은 삭제 대신 보관한다.
- 본인 작업 정정 권한을 검사할 공용 데이터에는 `created_by`를, 변경 이력에는 실제 작업자를 저장한다. 감사 로그의 작성자도 클라이언트 입력으로 결정하지 않는다.

| 공통 테이블 | 역할 |
|---|---|
| 인증 라이브러리 테이블 | 사용자·계정·세션·OAuth client/grant/token. 라이브러리 표준 스키마 사용 |
| `households` | 가족 이름·시간대 |
| `household_members` | 가족·사용자·owner/member·활성 상태. 가족/사용자 조합 유일 |
| `household_invites` | 소유자가 허용한 이메일·역할·만료/사용 상태 |
| `mutation_requests` | 작업 키·입력 해시·결과, 중복 변경 방지 |
| `activity_log` | 누가 웹/어느 AI를 통해 무엇을 변경했는지 |

## 3. 커피 원두

### 3.1 데이터 모델

| 테이블 | 주요 필드 |
|---|---|
| `coffee_brands` | 이름, 스토어 URL, 설명 |
| `coffee_beans` | 브랜드, 제품명, 상품 URL/정규화 키, 이미지 URL, 배전, 맛 설명, 상품 가격, 중량(g), 가격 확인일, 출처, version |
| `coffee_preferences` | 원두, 사용자, 상태(구매예정/먹어봄/미입력), 추천(추천/보통/비추천/미입력), 내 평가, version |
| `coffee_machines` | 가족 머신 이름, 분쇄·용량 설정 단위 설명 |
| `coffee_brew_settings` | 원두, 사용자, 머신, 분쇄 설정 숫자, 용량 설정 숫자, 메모, 기록일 |

모든 행에 가족 ID를 두고 연결된 브랜드·원두·머신도 같은 가족인지 검사한다. `coffee_preferences`는 `(household_id, bean_id, user_id)`당 한 행이다. 세팅은 날짜별로 보존하며 초기 화면의 “내 세팅”은 선택한 머신의 최신 기록이다.

원문 `(11, 6)`은 **분쇄도와 용량 설정값**이다. `6`을 실제 6g으로 해석하지 않는다. 머신·단위를 모르면 “기존 머신 / 기기 설정값”으로 표시한다. 실제 분쇄 원두 g·추출량 g·추출 시간은 필요해질 때 별도 필드로 추가한다.

가격은 판매 포장의 가격과 중량을 저장하고 `1kg 환산 가격 = 상품 가격 × 1000 / 중량(g)`으로 계산한다. 중량은 양수여야 하며 누락 시 환산 가격을 표시하지 않는다. 예: 200g에 15,000원이면 75,000원/kg이다. 배송비 포함 여부가 다르면 비교 조건을 표시한다. 기존 원본에 kg 가격만 있다면 별도 기준값과 출처로 보존하고 중량을 지어내지 않는다.

가격 이력·커피 재고는 MVP의 필수가 아니다. 현재 상품 정보의 확인일을 표시한다. 구매 내역·원두 잔량이 필요해지면 구매 테이블을 추가한다.

### 3.2 원본 요구사항과 초기 데이터

- 브랜드 목록, 원두 이름·브랜드·가격·상태·추천·배전·상품 링크·맛·세팅·내 평가를 모두 수용한다.
- 원문 **10개 브랜드, 11개 원두**를 seed 후보로 삼는다. 에스쇼콜라·프루티봉봉 등 원문의 추천·보통·비추, 숫자 세팅, “딸기향이 많이남” 메모를 보존한다.
- `비추`는 `비추천`으로 정규화하고 원문은 이관 자료에 보관한다. 기존 개인 평가·세팅 작성자는 원본 작성자인 소유자로 지정한다.
- 가격·배전·이미지·명시되지 않은 상태를 추정하지 않는다. 추천 여부만으로 일괄 “먹어봄” 처리하지 않는다.
- 상품 URL은 플랫폼·스토어·상품 ID로 중복 후보를 찾고 추적 쿼리를 제거한다. 다른 판매처의 동일 상품이나 같은 상품의 옵션을 확인 없이 병합하지 않는다.

### 3.3 시각화

- 원두 카드에서 이미지·브랜드·내 추천·내 머신 세팅을 바로 확인한다.
- 브랜드별 먹어본 원두 수, 배전별 분포, 같은 조건의 1kg 가격 비교를 제공한다.
- “나 / 가족 구성원 / 가족 전체” 필터를 둔다. 전체 평가는 추천·보통·비추천 분포로 표시하며 근거 없는 숫자 점수로 평균 내지 않는다.
- 현재 평가만으로 시간에 따른 취향 변화 그래프를 만들지 않는다. 추이가 필요해지면 평가 이력을 추가한다.

## 4. 와인 셀러

### 4.1 기존 스킬에서 유지·개선할 행동

와인 추가·소비·추천·목록 조회와 보유 와인잔 기반 추천을 유지한다. 같은 와인을 추가할 때 재고는 합산하되 **매번 구매가·구매일을 보존**한다. 시음 노트는 독립 기록으로 누적하며 가족마다 점수·재구매 의사를 구분한다.

“수량 부족 시 확인”은 **부족한 소비를 저장하지 않고 가능한 수량을 안내**하는 것으로 구현한다. 사용자 확인 후에도 음수 재고는 허용하지 않는다. “100개 단일 조회”는 모든 페이지를 조회하는 방식으로 바꾼다.

### 4.2 데이터 모델

| 테이블 | 주요 필드 |
|---|---|
| `wines` | 한글·영어 이름, 생산자(선택), 종류, 나라, 지역, 품종, 빈티지 상태/연도, 용량(선택), 표시 번호, version |
| `wine_purchases` | 와인, 구매일, 병수, 병당 구매가, 구매처(선택), 원본 출처 |
| `wine_stock_events` | 와인, 입고/소비/정정/취소/초기재고, 증감 병수, 기록 시각, 작성자, 구매 ID(선택), 취소 대상 이벤트 ID(선택), 사유 |
| `wine_tastings` | 와인, 작성자, 시음일, 점수(0~100/null), 노트, 재구매(true/false/null), 소비 이벤트 ID(선택) |
| `wine_glasses` | 잔 이름, 브랜드, 종류, 메모 |

현재 재고의 기준은 `SUM(wine_stock_events.delta)`다. 이벤트가 없는 제품의 재고는 0이다. 초기에는 잔량 캐시 컬럼을 두지 않아 원장과 잔량 불일치를 줄인다. 목록·차트는 같은 집계 SQL을 사용한다. 도메인 관계는 같은 가족인지 검사하며 가족/와인/시각에 조회 인덱스를 둔다.

재고 이벤트를 넣는 **모든 경로**는 같은 와인 행을 `FOR UPDATE`로 잠근 뒤 잔량을 계산한다. PostgreSQL READ COMMITTED에서 잠금 획득을 완료한 후 별도 조회로 합계를 구한다. 이후 이벤트·구매/시음·중복 요청 결과를 같은 트랜잭션에서 저장한다. 다른 격리 수준을 채택하면 직렬화 실패 재시도까지 검증한다.

수량은 양의 정수 입력으로 받고 업무 종류에 따라 부호를 결정한다. 소비·입고 취소 등으로 합계가 음수가 되면 거부한다. 같은 이벤트의 중복 취소는 유일 제약으로 차단한다. 이벤트는 임의 수정·삭제하지 않고 정정/취소 이벤트로 보완한다.

예: 9월 1일에 30,000원짜리 2병, 9월 8일에 35,000원짜리 1병을 구매하면 구매 기록 2개, 입고 이벤트 2개, 잔량 3병이다. 1병 소비 시 소비 이벤트를 추가해 2병이 된다. 과거 구매가를 덮어쓰지 않는다.

MVP에서는 어떤 구매분을 먼저 소비했는지까지 추적하지 않는다. 잔여 재고의 정확한 취득 원가·FIFO 손익 차트는 제공하지 않는다. 필요해지면 구매 로트별 소비 배분을 추가한다.

### 4.3 와인 식별과 시음

- 같은 이름·빈티지 검색은 중복 **후보 조회**다. 생산자·큐베·용량을 확인 가능한 범위에서 대조한다. 이름이 같다는 이유로 자동 병합하지 않는다.
- 빈티지는 `year / non_vintage / unknown`으로 구분한다. NV와 판독 실패는 다른 상태다.
- 기존 와인은 안정적인 `wine_id`로 구매를 추가한다. 여러 후보면 사용자에게 선택하게 한다.
- 시음은 소비 없이도 기록할 수 있다. 재구매 미평가와 “안 함”을 구분한다.
- 노트 문자열에 날짜를 붙여 갱신하는 대신 `tasted_on`을 저장해 `(YYYY-MM-DD)`로 표시한다. 가족별 여러 시음을 시간순으로 조회한다.
- 기존 국가·와인 종류·와인잔 종류를 보존한다. 품종처럼 복수 값이 가능한 항목은 단일 선택으로 축소하지 않는다.

### 4.4 추천과 시각화

MCP는 보유 와인, 개인별 시음, 보유 잔 등 추천 근거를 반환한다. AI가 음식/상황에 맞는 최대 3개를 골라 이유·온도·잔·디켄팅 의견을 설명한다. 보유 와인이 적으면 가능한 수만 추천하고, 없으면 빈 결과를 안내한다.

추천에는 재고 조회 시각·상세 링크를 포함한다. 실제 소비 시 재고를 다시 확인한다. 저장된 사실과 일반적인 와인 지식에 따른 제안을 구분하며, AI 설명을 검증된 제품 정보로 자동 저장하지 않는다. Vivino는 영어 이름·빈티지를 URL 인코딩한 검색 링크로 제공한다.

차트는 종류별·국가별 **현재 병수**, 기간별 **소비 병수**, 본인/가족별 시음 점수를 우선한다. 소비 취소 이벤트를 반영해 유효한 소비량을 집계한다. 점수의 작성자와 미평가를 표시한다. 구매 금액 추이는 완전한 기록이 시작된 시점부터 제공하며 알려지지 않은 과거 지출을 0원으로 처리하지 않는다.

## 5. MCP 도구 초안

아래는 초기 공개 업무 범위다. 정확한 입력/출력 스키마와 예제는 코드와 함께 확정한다. 가족·작성자는 인증에서 결정하고 모든 쓰기 도구는 공통 idempotency 규칙을 따른다.

| 도구 | 주요 입력 | 결과·규칙 |
|---|---|---|
| `coffee_list_brands`, `coffee_create_brand` | 검색/페이지 또는 이름·URL·설명 | 브랜드 ID·목록 |
| `coffee_list_beans`, `coffee_get_bean` | 필터/페이지 또는 bean ID | 제품·가족 평가·세팅 |
| `coffee_create_bean`, `coffee_update_bean` | 상품 정보 또는 ID·변경값·expected_version | 저장 ID·변경 결과, 가격/중량 검증 |
| `coffee_save_preference` | bean ID·내 상태·추천·평가·expected_version | 본인 평가만 저장. 최초 생성 version은 null |
| `coffee_list_machines` | 페이지 | 세팅에 사용할 머신 ID |
| `coffee_log_brew_setting` | bean ID·machine ID·분쇄·용량 설정·메모 | 새 세팅 기록 |
| `wine_list`, `wine_get` | 필터/페이지 또는 wine ID | 와인·잔량·최근 이력 |
| `wine_create` | 이름·종류·빈티지 등 | 제품 ID, 재고 변화 없음 |
| `wine_receive_stock` | wine ID·병수·단가·구매일 | 구매·입고를 함께 저장, 잔량 반환 |
| `wine_consume` | wine ID·병수(기본 1)·선택 시음값 | 차감·시음 원자적 저장, 부족하면 거부 |
| `wine_log_tasting` | wine ID·점수·노트·재구매·시음일 | 재고 변화 없는 시음 |

| `wine_get_pairing_context` | 종류/국가 등 구조화 필터·페이지 | 보유 와인·잔·기록·조회 시각·추가 페이지 여부 |
| `household_get_summary` | 기간·도메인(선택) | 권한 있는 도메인의 요약 |

머신 등록·가족 관리·재고 취소/정정은 웹에서 먼저 제공한다. 머신 목록은 AI 세팅 등록에 필요해 MCP에 둔다. `wine_create` 후 입고가 실패하면 제품만 존재할 수 있다. AI는 완료 단계와 재시도할 단계를 구분해 안내하고 제품 생성을 반복하지 않는다.

`wine_get_pairing_context`는 서버가 LLM을 호출하는 도구가 아니다. 음식 해석과 추천 추론은 외부 AI가 맡는다. 가족 요약은 `coffee:read`만 있으면 와인 정보를 반환하지 않으며, 지정한 도메인의 scope가 없으면 권한 오류를 반환한다.

## 6. 기존 데이터 이관

원본 와인 스킬은 행동 요구사항·필드 매핑의 참고 자료다. 이 문서 작성 중 Airtable·Google의 실제 데이터는 조회하지 않았다. 기존 스킬의 특정 MCP 플랜 제약을 새 서비스에 그대로 옮기지 않는다.

1. Airtable 와인·와인잔을 모든 페이지에 걸쳐 export하고 원본 스냅샷을 보관한다. 인터페이스가 일부 행만 보여줄 수 있으므로 테이블 전체 건수와 대조한다.
2. 원본 record ID·표시 ID·이름·빈티지·수량·가격·날짜·평가·잔 종류를 보존한다. 이관 mapping의 `(source_system, source_table, source_record_id)`를 유일하게 관리해 재실행 중복을 막는다. 기존 표시 번호를 유지하면 sequence의 다음 값도 조정한다.
3. 현재 수량은 이관일 기준 `opening_balance` 이벤트로 가져온다. 기존 구매가·구매일은 원본 메타데이터로 보존한다. 과거 소비·구매분을 모르므로 구매 이력을 지어내거나 초기 재고에 다시 입고를 더하지 않는다.
4. 누적 시음 노트는 원문을 보관한다. 날짜·경계가 명확한 구간만 시음으로 분리하며 단일 점수를 모든 과거 시음에 복제하지 않는다. 분리 불가능한 값은 “이관 원문”으로 표시한다. 미입력/false 구분이 불명확한 재구매 checkbox도 원본값과 해석을 분리한다.
5. 커피는 Apps Script/Sheets 원본 유무부터 확인한다. 있으면 초기 목록과 대조하고 없으면 브랜드 10개·원두 11개로 시작한다. 같은 URL의 기존 메모를 조용히 덮어쓰지 않는다.
6. 시험 DB에서 와인별 잔량·총 병수·종류별 합계·잔 수·원두 수·평가 누락을 대조한다. 원본과 변환 실패 목록을 남긴다.
7. 전환 시 기존 시스템의 쓰기를 잠시 중단하고 최종 export를 반영한다. 검증 후 웹/MCP를 새 DB로 전환하고 기존 시스템은 읽기 전용으로 보관한다.
8. 실패 시 새 DB의 쓰기를 멈추고 전환 후 변경을 export해 조정한다. 옛 시스템을 단순 재활성화해 두 곳에 쓰지 않는다.

기존 와인 스킬의 Airtable 호출은 서비스 가동 후 도메인 MCP 호출로 교체한다. DB 필드 ID·재고 갱신 알고리즘은 서버가 책임지고, 스킬에는 추천 방식·응답 형식·모호한 대상 확인 등 대화 규칙을 남긴다.
