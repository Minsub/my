# 커피 페이지 동작 기준

2026-11-02 구현 기준. 원본 DESIGN.md의 이미지 요구사항보다 이 문서를 우선한다.

목록은 "어떤 원두를 먹어봤는지 확인하고 다음에 살 원두를 고르는" 화면이다. 머신 세팅은 상세에서 본다.

## 원두 목록 `/coffee`

- 행 구성: 브랜드 대표 이미지(없으면 첫 글자) · 브랜드/원두명/상품 페이지 아이콘/맛과 향/배전 · 판매 가격 · 평가(경험·추천 태그, 추천 인원, 메모, 내 평가 기록). 상품 페이지 아이콘은 `product_url`이 있을 때만 새 탭으로 연다.
- 모바일(760px 이하)은 이미지·원두·가격 한 줄 아래에 평가를 **경험·추천 태그 한 줄**로만 보여준다(예: `먹어봄 비추천`, `구매예정`). 추천 인원·메모·기록 버튼은 숨기고 넘치는 태그는 잘라 줄바꿈하지 않는다. 평가 기록은 상세에서 한다.
- 가격은 용량별 옵션 중 **가장 비싼 옵션 하나**를 `65,000원 / 1kg`처럼 한 줄로 보여준다(가격이 같으면 중량이 큰 쪽, 가격이 모두 없으면 첫 줄). 중량이 없으면 가격만, 가격이 없으면 `가격 미입력`. 1000g 단위는 kg로 표시한다. 기준은 `src/lib/coffee.ts`의 `mainPrice`·`weightLabel`이다. 0원과 미입력을 구분한다.
- 1kg 환산 가격은 표시하지 않는다(목록·상세·정렬 모두 없음).
- 이름순, 브랜드순, 판매 가격 낮은순/높은순을 제공한다. 가격 정렬은 대표 옵션 기준이다. 가격을 계산할 수 없는 항목은 마지막이고, 동일 가격은 이름순이다.
- 검색 대상은 원두명·브랜드명·맛과 향이다. 브랜드·경험·추천·평가 사용자 필터와 초기화를 제공한다.
- **경험(구매예정/먹어봄)은 저장값이 아니라 취향 기록 여부다.** 선택한 평가 사용자가 그 원두에 취향을 기록했으면 먹어봄, 아니면 구매예정이다. 사용자 전체를 고르면 누군가 기록했으면 먹어봄이다. 등록한 원두는 모두 구매예정으로 시작한다. 기준은 `beanStatus`다.
- 추천 칩은 선택한 평가 사용자 기준이다. `누군가 추천`(`recommend=any-추천`)만 구성원 누구든 추천한 원두를 남긴다. 목록의 `추천 N명`은 사용자 필터와 무관하게 항상 표시하고 추천한 구성원 이름을 title로 준다.
- 원두 보관(보관함)은 없다. 모든 원두가 목록에 나온다. DB의 `coffee_beans.archived` 열은 이전 코드 호환용으로만 남았다.
- URL 키: `q`, `brand`, `recommend`, `status`, `person`, `sort`. 탭 왕복과 상세의 목록 복귀 링크가 보존한다. 데모도 `view`와 함께 같은 쿼리를 전달하며 저장하지 않는다.

## 원두 등록·수정

- 용량별 가격을 여러 줄 입력한다(최대 10줄, `줄 추가`/휴지통). 중량과 가격이 모두 빈 줄은 저장하지 않는다. 한 줄은 중량 또는 가격 중 하나만 있어도 된다.
- 저장은 옵션 전체 교체다(`coffee_bean_prices`를 지우고 입력 순서대로 다시 넣는다). 웹·MCP 모두 `prices: [{weight_g, price}]`로 보낸다.
- 원두 이미지 입력은 없다. 기존 `image_url`은 MCP 계약 호환을 위해 유지하며 수정 폼이 지우지 않는다.

## 취향 기록

- 추천(추천/보통/비추천)과 메모만 입력한다. 경험을 고르는 칸은 없다. 기록하면 그 사용자에게 먹어봄이 된다. 아무것도 고르지 않고 저장해도 "먹어봤다"는 기록으로 남는다.
- 서버는 `coffee_preferences.status`를 항상 `먹어봄`으로 쓴다(열은 호환용). MCP `coffee_save_preference`는 `status` 입력을 받지 않는다.
- 평가 내용은 사용자별로 분리하고 추천 집계는 공유한다.

## 원두 상세 `/coffee/beans/{id}`

- 브랜드 대표 이미지와 브랜드 링크, 경험·내 추천 태그, 용량별 가격 표(포장 중량·판매 가격. 옵션이 둘 이상이면 대표 옵션 굵게, 옵션이 없으면 `가격 미입력`), 상품 보기, 정보 수정, 사용자별 평가, 머신 세팅 기록.
- 머신 세팅은 로그인한 사용자의 기록이다. 분쇄도와 용량은 기기의 설정 숫자이며 g이 아니다. 머신은 공간에 하나이고 서버가 `커피 머신`을 만들어 쓴다. 머신 등록 화면과 머신 MCP 도구는 없다.

## 브랜드 스토어 `/coffee/brands`

- 카드마다 대표 이미지(72px, 없으면 첫 글자), 원두 수 링크, 스토어 링크, 이미지 올리기, 수정 버튼. 이미지 올리기·수정은 등록자 또는 관리자만 보인다.
- **대표 이미지는 웹에서만 올린다.** MCP 도구는 없고 `/api/coffee/brands/{id}/photo`는 MCP 토큰을 받지 않는다. 저장 규칙은 와인 사진과 같다(브라우저 1200px JPEG → 서버 1000px WebP, 300KB 상한, 메타데이터 제거). [사진 저장 방식](../image-storage.md) 참고.
- 이미지를 바꾸면 브랜드 version이 오르고 화면은 `?v=version` 주소로 받는다. 같은 화면에서 두 번 올리면 두 번째는 VERSION_CONFLICT다(새로고침 후 다시).
- 브랜드 이름과 원두 수 링크는 그 브랜드의 원두 목록으로 이동한다. 원두 목록의 브랜드 이름·이미지는 브랜드 탭의 해당 카드로 이동한다.

## 데이터 (019 migration)

- `coffee_bean_prices(household_id, bean_id, position, weight_g, price)`: 원두 삭제 시 CASCADE. 기존 `coffee_beans.price·weight_g`를 position 0으로 옮겼다. 두 열은 남겨 두었고 새 코드는 읽지도 쓰지도 않는다.
- `coffee_brand_photos(brand_id, content, content_hash, updated_at)`: 스냅숏은 브랜드에 `has_photo`만 넣는다. `db:export`는 `brand_photos`로 base64를 포함한다.
- 기존 취향 기록 중 추천·메모 없이 `구매예정`만 남긴 행은 기본값과 같아 지웠고, 나머지는 `먹어봄`으로 맞췄다.
- 이전 코드 호환 열(`price`, `weight_g`, `archived`, `status`)은 운영 배포가 안정된 뒤 별도 migration으로 지울 수 있다.
